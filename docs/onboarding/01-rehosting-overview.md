# 01. 리호스팅 개요

> 이 저장소가 무엇을 하는지, 부팅 체인의 어디를 어디까지 실행하는지, 왜 그것이 커널
> 이미지만 실행하는 것과 다른지.

---

## 1. 리호스팅이란

기기 없이 펌웨어를 **원본 바이너리 그대로** 다른 환경에서 실행시키는 것.
재구현이 아니다. 펌웨어 코드는 손대지 않고 그 코드가 접근하는 **환경**을 만든다.

| | 에뮬레이션 | 리호스팅 |
|---|---|---|
| 대상 | 하드웨어 전체 | 펌웨어가 실제로 접근하는 부분만 |
| 목표 | 정확한 재현 | 코드가 계속 실행되게 하는 것 |
| 미모델 주변장치 | 구현 필요 | 접근 시점에 관찰 후 그 창만 모델링 |

---

## 2. 휴대폰의 부팅 순서

각 단계는 다음 단계를 검증하고 넘긴다. 이것이 verified boot chain 이다.

| # | 단계 | 하는 일 | 이 저장소에서 |
|---|---|---|---|
| ① | BootROM | SoC 내장 ROM. 변경 불가 | 실행 안 함. **남기는 상태만** 모델링 |
| ② | 1차 부트로더 | DRAM 초기화, 보안 환경 설정 | 평문이면 **실제 실행**. 암호화면 건너뛰고 기록 |
| ③ | 부트로더 | S-Boot / LK / aboot. 셸, 파티션·커널 적재 | **실제 실행** |
| ④ | EL3 모니터 | 보안 모니터(TF-A). PSCI·SMC | SMC shim 으로 모델링 |
| ⑤ | EL2 하이퍼바이저 | 최근에는 커널에 내장 | 커널 소관. 가로채지 않음 |
| ⑥ | 커널 | Linux 시작 | **실제 실행.** 부트로더가 적재한다 |
| ⑦ | init 1단계 | rootfs 탐색·마운트 | **실제 실행** |
| ⑧ | init 2단계 | 안드로이드 서비스 기동 | 미해결 (`/data` FBE → TEE) |
| ⑨ | Android UI | 홈 화면 | 범위 밖 (디스플레이·GPU·모뎀 없음) |

### ARM Exception Level

| EL | 실행 주체 | 리호스팅에서의 의미 |
|---|---|---|
| EL3 | 보안 모니터 | 부트로더가 `smc` 로 요청한다. shim 으로 응답 |
| EL2 | 하이퍼바이저 | `kvm-arm.mode=protected` 면 커널이 EL2 를 쓴다. 가로채면 안 된다 |
| EL1 | OS 커널 | |
| EL0 | 유저스페이스 | |

잘못된 EL 로 진입시키면 증상이 엉뚱한 곳에서 나타난다. 그래서 **계층** 개념을 둔다
→ [04-loop-and-honesty.md](04-loop-and-honesty.md)

## 3. 실행 범위

```
컨테이너 적재 → stage0 → stage1 → … → 부트로더 → 커널 → rootfs
                  ↑                        │
            리셋 PC (도출값)          부트로더가 매체에서 커널을 읽어 적재
```

- **`-kernel Image` · `-dtb` · `-initrd` 를 쓰지 않는다.** 부트로더가 매체에서 커널을
  읽고 검증하고 DTB 를 조립한다. 떠먹이면 커널 이미지만 실행하는 것과 구별되지 않는다
- 암호화되었거나 패키지에 없는 스테이지는 **다음 실행 가능 스테이지로 진입을 재지정**한다
- 건너뛰기의 정당성 조건: **이후 스테이지가 건너뛴 스테이지의 메모리를 읽지 않아야 한다**
- **대신할 값을 지어내지 않는다.** 이후 단계가 요구하면 그것은 채울 대상이 아니라
  보고할 사실이다

---

## 4. 목표 단계와 등급

스테이지 수가 펌웨어마다 다르므로 `stage_map.json` 이 세고, 그만큼 앞이 만들어진 뒤
공통 뒷부분이 붙는다.

```
stage_entry × N → <표면> → medium_up → partitions → verify_ok
                → kernel_entry → kernel_alive → userspace → rootfs
```

| 등급 | 범위 | 뜻 |
|---|---|---|
| **F1** | 스테이지 진입 전부 + 표면 | 부트로더 체인이 실제로 동작 |
| **F2** | F1 + 매체·파티션·검증·커널 진입·**커널 실행** | 커널이 실제로 실행 |
| **F3** | F2 + userspace·rootfs | rootfs 마운트까지 완주 |

- **`kernel_entry` ≠ `kernel_alive`.** 앞은 부트로더가 `Starting kernel...` 을 출력한
  것, 뒤는 커널이 `Linux version` 을 출력한 것. 점프 선언만으로 도달을 세면 **커널이
  실행되지 않은 실행을 완주로 보고하게 된다**
- 실제 사례가 있다. `Starting kernel...` 이 콘솔 마지막 줄이고 그 뒤로 한 줄도 없었는데
  사다리는 `kernel_entry` 를 도달로 세고 있었다
- **커널이 조용하면 커맨드라인부터 본다.** `console=ram` 이면 로그가 RAM 버퍼로 가서
  커널이 완벽히 떠도 시리얼에 안 나온다. 침묵은 실패의 증거가 아니다
- **F1 은 스토리지 모델 없이 도달 가능하다.** 첫 스테이지는 앞 단계가 남긴 함수
  포인터로 블록을 읽는다. F1 을 확정한 뒤 F2 로 간다

## 5. 무엇이 어려운가

| # | 유형 | 무슨 일이 일어나나 | 담당 |
|---|---|---|---|
| 1 | 주변장치 부재 | 없는 주소 접근 → data abort, 또는 무한 폴링 | `fixer-memory` |
| 2 | 보안 환경 부재 | `smc` → EL3 모니터 없음 → undefined instruction | `fixer-el3` |
| 3 | 이전 단계 부재 | 첫 스테이지가 앞 단계의 함수 포인터를 호출 | `fixer-bootflow` |
| 4 | 무결성 검사 | 서명 검증이 이 환경에서 실패 | `fixer-secureboot` |
| 5 | 스토리지 컨트롤러 | 벤더 드라이버가 문서 없는 레지스터를 폴링 | `fixer-storage` |
| 6 | 커널 보안 게이트 | FIPS·DEFEX·SELinux 가 panic | `fixer-kernel` |

### 기술적 실패보다 위험한 것: 허위 통과

| 수법 | 왜 허위인가 |
|---|---|
| 적응형 토글 ("12회 읽은 뒤 값 변경") | 잘못된 분기로 보내며 다른 펌웨어에서 재현되지 않는다 |
| 머신이 프롬프트 문자열을 출력 | 우리가 출력한 것이다 |
| 머신이 자기 수신 버퍼를 채움 | 자기 자신과 대화한 것이다 |
| 트램폴린으로 핸들러 강제 호출 | 입력에서 디스패처로 가는 경로가 성립하지 않았다 |
| 서명 검증을 패치로 무력화 | 검증을 거쳤다는 주장 자체가 성립하지 않는다 |

이 저장소의 상당 부분(출력 출처 검증, 게이트 3항, 정직성 규칙)은 **허위 통과를 코드로
막는 장치**다 → [04-loop-and-honesty.md](04-loop-and-honesty.md)

## 6. 왜 이 지점이 중요한가

| 도달 지점 | 가능해지는 것 |
|---|---|
| 부트로더 표면 | 명령 파서에 **입력을 넣어 시험**할 수 있다 |
| 스테이지 연속 실행 | 각 단계가 다음에 무엇을 넘기는지 **관찰**할 수 있다 |
| 서명 검증 통과 | 검증 코드가 **실제로 수행**됐음을 양방향으로 증명 |
| 커널 진입 | 부트로더의 부팅 결정 로직을 끝까지 추적 |
| rootfs 마운트 | 벤더 스토리지 컨트롤러 사양을 복원했다는 증명 |

- **실기기로는 불가능한 관측**: 부트로더·커널 초기화 구간은 디버거가 붙지 않는다.
  QEMU 는 모든 명령과 임의 시점의 메모리를 준다
- **기기 손상 없는 반복**: 부트 파티션을 잘못 건드리면 실기기는 복구 불가가 된다
- **상위 권한 공격면**: 부트로더는 커널보다 먼저, 더 높은 권한으로 실행된다
- **문서 없는 인터페이스 복원**: 데이터시트 없이 드라이버만 보고 컨트롤러 사양을 복원
- **재현성**: 재현 키트로 빌드 없이 같은 상태를 재현
