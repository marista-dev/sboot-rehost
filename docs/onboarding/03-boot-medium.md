# 03. 부팅 매체와 스토리지 컨트롤러

> **읽고 나면**: 부트로더가 커널을 읽어 올 매체를 왜 합성해야 하는지, 어떻게 만드는지,
> 컨트롤러 모델이 왜 두 번 검증되는지 알 수 있다.

---

## 1. 왜 매체가 필요한가

통합 체인은 커널을 QEMU 가 넘겨주지 않는다. 부트로더가 기기에서 하던 대로
**컨트롤러를 올리고 → 파티션 테이블을 읽고 → 이름으로 파티션을 찾아 → 이미지를 꺼낸다.**

그러려면 우리가 모델링하는 매체에 그 파티션들이 **부트로더가 찾는 이름으로** 실제로 있어야 한다.

매체를 읽는 주체는 셋이다.

| 읽는 주체 | 무엇을 | 필요 시점 |
|---|---|---|
| 첫 스테이지 | 파티션 테이블 | 이전 단계가 남긴 함수 포인터로 읽으므로 **컨트롤러 모델 불필요** |
| 부트로더 | boot image · 검증 자료 | 자체 드라이버로 컨트롤러를 직접 구동 |
| 커널 | rootfs | 빌트인 벤더 드라이버로 **같은 컨트롤러**를 구동 |

**같은 모델을 두 드라이버가 차례로 구동한다.** 한쪽에 맞춘 모델은 다른 쪽에서 깨지므로,
이 구조 자체가 검증 장치다 → 검증 항목 5

---

## 2. UFS 와 LUN — 배경

UFS 는 임베디드 저장장치 표준이다. 호스트(SoC) 쪽 컨트롤러가 **UFSHCI**, 장치 쪽이 UFS
디바이스이며, 그 사이는 UniPro 링크로 연결된다.

**LU(Logical Unit)** 는 하나의 물리 장치를 논리적으로 나눈 단위다. SCSI 의 LUN 과 같은 개념이며,
기기에서는 보통 부팅용 LU 와 사용자 데이터 LU 가 분리되어 있다.

| 계층 | 역할 |
|---|---|
| UFSHCI 레지스터 | 호스트가 명령을 올리고 완료를 확인하는 창구 |
| UTRD | 전송 요청 서술자. 명령·응답 버퍼와 데이터 스캐터 목록을 가리킨다 |
| UPIU | 실제 명령·응답 패킷. **LUN 은 헤더의 세 번째 바이트** |
| PRDT | 데이터 스캐터 목록. 항목 간 간격(stride)이 벤더 확장으로 넓어질 수 있다 |

LUN 을 잘못 읽으면 드라이버는 장치를 붙이고도 파티션을 열거하지 못한다.

## 3. 매체 합성 — `build_lu.py`

```bash
bash scripts/py.sh build_lu.py <workdir> --out <workdir>/fw/lu0.img
```

유효한 GPT 디스크를 만든다: 보호 MBR, 주 헤더, 128개 엔트리 배열, 백업 헤더, 각각의 CRC32.
각 파티션은 지정한 파일로 채운다.

### 파티션 이름은 도출값이다

부트로더는 파티션을 **이름으로** 조회한다. 우리가 지어낸 이름은 펌웨어가 영원히 찾지 못하는
파티션이며, 그 실패는 한참 뒤에 검증 오류나 조용한 다운로드 모드 진입으로 나타난다.

이름은 `lu_manifest.json` 에서 온다. static-analyzer 가 부트로더 문자열에서 도출해 기록한다.

```json
{
  "block_size": 4096,
  "partitions": [
    {"name": "boot",       "source": "fw/boot.img"},
    {"name": "vbmeta",     "source": "fw/vbmeta.img"},
    {"name": "keystorage", "source": "02_unpacked/keystorage.bin"}
  ]
}
```

매니페스트가 없으면 문서화된 기본 이름을 쓰되, **기본값을 썼다고 결과에 명시**한다.
입력 게이트가 기본 패턴을 쓸 때와 같은 방식이다 — 도출하지 못한 것을 도출한 것처럼 두지 않는다.

### 블록 크기

512 와 4096 중 어느 쪽인지는 컨트롤러가 보고하는 값과 GPT 서명 위치로 확정한다.
어긋나면 첫 블록만 읽고 서명을 찾지 못하거나, 그럴듯한 쓰레기를 읽는다.

### Android sparse 이미지는 디스크가 아니다

`super.img` 등은 sparse 포맷이라 그대로 붙이면 파티션 테이블이 없다. raw 로 변환한 뒤
GPT 를 씌운 LU 를 합성해야 커널이 파티션을 열거한다.

## 4. 컨트롤러 모델

데이터시트가 없으므로 **드라이버를 계측기로 쓴다.** 실제 벤더 드라이버가 어떤 레지스터를
폴링하고 어떤 값을 기다리는지 관찰한 뒤, 관찰한 것만 모델에 채운다.

### 레지스터 주소는 DTB 가 권위 출처다

DTB 의 스토리지 노드가 컨트롤러 레지스터 창들과 인터럽트 번호를 명시한다.

> **4바이트 리터럴 스캔으로 MMIO 주소를 찾지 않는다.** AArch64 는 상수를 MOVZ/MOVK 로
> 조립하므로, 리터럴 스캔은 우연히 일치한 바이트열을 찾고 실제 베이스는 놓친다.
> DTB 값을 기준으로 삼고, 코드에서 MOVZ/MOVK 로 복원해 교차 확인한다.

### 자주 만나는 정지점

상세는 `knowledge/faults_storage.md` 에 있다. 대표적인 것만:

| 정지점 | 신호 | 처방 |
|---|---|---|
| `poll_stall` | 같은 오프셋 읽기가 수백 회 반복 | **기다리는 비트만** 세운다. 전체 비트를 세우면 잘못된 분기로 간다 |
| `irq_edge_level` | 완료 비트를 세웠는데도 타임아웃 | 인터럽트는 레벨 트리거여야 한다. 펄스는 놓친다 |
| `is_bit_layout` | 링크는 되는데 전원 모드 전환 실패 | 상태 레지스터 비트 위치를 드라이버 마스크에서 도출 |
| `prdt_stride` | 읽기는 성공하는데 내용이 다름 | 스캐터 항목 간격을 실측. 벤더 확장으로 넓어져 있다 |
| `upiu_field_off` | 장치는 붙는데 파티션이 없음 | UPIU 헤더의 LUN·전송 길이 필드 위치 수정 |
| `block_size` | LBA0 만 읽고 GPT 서명 못 찾음 | 백킹 이미지에서 서명 위치를 찾아 블록 크기 확정 |

### 벤더 드라이버가 `.ko` 일 필요는 없다

커널에 빌트인(`CONFIG_SCSI_UFS_*=y`)이면 `.ko` 는 설계상 존재하지 않는다. 그래도 벤더
드라이버는 커널 안에 있고 모델을 구동한다. **`.ko` 부재만으로 불가 판정을 내리면 도달 가능한
실행을 거부하는 것이다.** `.ko` 도 없고 커널 이미지에도 없을 때만 `BLOCKED_KO` 다.

## 5. 완료 지점

| 마일스톤 | 커널이 출력하는 것 | 뜻 |
|---|---|---|
| `medium_up` | 링크 확립 | 컨트롤러가 응답 |
| `partitions` | 부트로더의 파티션 조회 성공 | 부트로더 쪽 완료 |
| `partitions_up` | 파티션 열거 | **커널 쪽 최소 완료** |
| `super_mounted` | 논리 파티션 마운트 | 해당 이미지가 있는 펌웨어만 |

`super.img` 가 없는 펌웨어(system/vendor 분리)는 구조상 마지막 줄을 출력할 수 없으므로
목표 단계에 넣지 않는다.

`partitions_up` 에 도달하지 못했다면 컨트롤러 모델이 미완성이라는 뜻이다.
**도달 지점을 정직하게 보고하고 REAL 로 표기하지 않는다.**
