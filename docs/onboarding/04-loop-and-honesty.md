# 04. 회차 루프와 정직성

> **읽고 나면**: 루프가 무엇을 반복하는지, 정지를 어떻게 판정하는지, 허위 통과를 막는
> 장치가 무엇인지 알 수 있다.

---

## 1. 한 문장

> **실행해서 최초 예외를 보고 → 정지점에 이름을 붙이고 → 한 곳만 고치고 →
> 다시 빌드해 다시 실행한다.**

```
   실행 (QEMU)                     run_full.sh
      ↓
   실행 지문 추출                   스크립트
      ↓
   이름 붙이기                      fault-classifier
      ↓
   한 곳만 고치기                    담당 fixer
      ↓
   검문 + 재빌드                    check_change.sh · sync_machine.sh · ninja
      ↓
   (반복)
```

측정과 정지 판정은 스크립트가, 해석과 수정은 에이전트가 맡는다. 이 분리가 없으면
"고칠 것이 있어야 하니까" 없는 원인을 지목하게 된다.

---

## 2. 실행 지문

정지점의 식별자다.

```
실행 지문 = (최초 예외의 ESR/FAR/ELR, 마일스톤, 콘솔 바이트, 콘솔 고유 줄 수, 예외 수 자릿수)
```

### 왜 최초 예외인가

예외 핸들러가 자기 컨텍스트를 저장하다 다시 폴트하면 abort 가 중첩된다. FAR 이 반복마다
0x20 씩 증가하다가 타임아웃이 끊은 지점에서 멈추므로, **트레이스의 마지막 FAR 은 재귀의
위치이지 원인이 아니고 회차마다 값이 달라진다.**

그 값을 지문에 쓰면 두 가지가 동시에 망가진다.

- 분류기가 실재하지 않는 정지점을 지목한다
- 정체 카운트가 영원히 0 이 되어 소진·재도출·계층 재검토가 발화하지 않는다

원인은 `fingerprint.json` 의 `origin` 에 있다. 마지막 FAR/ELR 은 따로 보존하되 진단
입력으로 쓰지 않는다. 예외 수는 자릿수로 비교한다 (2.86M 과 2.88M 은 같은 관측이다).

### 부팅 깊이

목표 단계가 한 칸일 때는 마일스톤이 비어 있어도 실행이 전진할 수 있다.
**콘솔 고유 줄 수**가 그 깊이를 센다. 재시도 루프가 같은 한 줄로 수백 KB 를 출력하므로
바이트 수는 전진의 지표가 되지 못한다.

`timeout_bound=true` 는 더 오래 실행하니 콘솔이 더 나왔다는 뜻이다. 그 한계는 펌웨어가
아니라 우리 실행 시간이므로 fixer 를 배정하지 않는다.

### 실행되지 않은 회차는 회차가 아니다

QEMU 가 시작조차 못 하면 지문이 전부 0 으로 안정된다. 이는 정체로 읽혀 "구조상 도달 불가"
판정이 된다 — 실행된 적 없는 펌웨어에 대해서. 실행 스크립트가 종료코드와 트레이스·콘솔
0바이트를 검사해 실행 실패를 세우고, 파이프라인은 그 회차에 `BLOCKED_ENV` 로 정지한다.

## 3. 계층 — 회차로 고칠 수 없는 것

fixer 는 **이미 있는 머신 소스의 한 곳**을 고친다. 머신이 **무엇을 전제로 생성됐는지**는
고치지 못한다.

| 계층 | 예 | 고치는 주체 |
|---|---|---|
| loop | 미매핑 메모리 영역, 미처리 SMC id, 종료되지 않는 폴링 | fixer (회차당 1건) |
| build | 진입 EL, 진입 PC, 스테이지 적재 주소, 메모리 골격, CPU 타입, 건너뛰기 재지정 | 머신 재생성 |

전제가 틀리면 fixer 는 증상만 처치한다. 벡터 베이스를 손상시키는 명령을 NOP 으로 바꾸는 것은,
이미지를 잘못된 EL 로 진입시킨 것이 원인일 때 다음 증상을 남겨둘 뿐이다.
**한 정지점으로 수십 회차를 소모하는 상황이 이렇게 생긴다.**

효과 없는 변경(변경했으나 지문 불변)이 임계를 넘으면 계층 재검토가 요청되고, supervisor 가
라우팅 전에 머신 소스와 `stage_map.json` 을 읽어 판정한다.

## 4. 정지 판정

**회차 수와 소요 시간은 정지 사유가 아니다.** 시도할 수단이 남아 있는 한 계속한다.

### 시도 소진

셋이 동시에 성립할 때만 인정한다.

```
(지문 정체 또는 A↔B 진동)
AND static-analyzer 재도출에서 새 사실 0
AND 담당 fixer 전원이 "시도할 변경 없음"
```

- 정체는 마지막 한 회차가 아니라 **최근 창(기본 3회차)** 으로 판정한다. 한 회차의 일시적
  변화가 수십 회차의 정체를 지우면 소진은 영원히 성립하지 않는다.
- "새 사실 0" 은 분석가의 자기 신고가 아니라 **도출표에 늘어난 줄을 센 값**이다.
- "fixer 소진" 도 **실제로 질의한 fixer 의 답변**이어야 한다. 아무도 부르지 않은 회차를
  전원 포기로 기록하면 소진 조건이 거짓으로 성립한다.

### 에이전트가 뒤집을 수 없다

`stop=true` 인데 supervisor 가 계속을 지시하면 파이프라인이 강제 정지하고 모순을 기록한다.
"한 번만 더" 가 정직성을 이기지 못하게 하는 장치다.

### 정지는 인계다

정지 시 `RESUME.md` 가 자동 생성된다.

- 도달 지점과 근거 로그 경로
- 마지막 지문과 왜 거기서 멈췄는지
- **시도한 변경 전부와 각각이 지문을 움직였는지**
- 아직 시도하지 않은 수단
- 재개 명령

검증됨으로 표기하지 않으며, 같은 명령으로 재개할 수 있다.

## 5. 정직성 규칙

| # | 규칙 | 집행 |
|---|---|---|
| 1 | 추측 스텁 금지 (특히 적응형 토글) | 분류기가 `unknown` 이면 재도출 |
| 2 | 우회는 우회로 표기 | `check_change.sh` |
| 3 | 모든 주소·구조·바이트열은 분석으로 도출 | `static-analyzer` |
| 4 | 하드코딩을 분석처럼 표기하지 않는다 | 문서 검토 |
| 5 | 도달하지 못한 지점은 그렇게 기록 | `verify.py` |
| 6 | 성공 판정은 실행 증거로만 | `verify.py` + verifier |
| 7 | 머신 내부에서 입력을 만들지 않는다 | 출력 출처 검증 (매 회차) |

### 규칙 1 — 적응형 토글이 특히 위험한 이유

"12회 읽은 뒤 값을 바꾼다" 같은 응답은 드라이버를 눈에 띄게 전진시킨다. 그러나 펌웨어를
기기에서라면 가지 않았을 분기로 보내며, 다른 펌웨어에서는 재현되지 않는다.
**상수 응답만 허용한다.** 기다리는 비트를 모르면 추측하지 말고 도출한다.

### 규칙 7 — 출력 출처 검증

콘솔에 목표 문자열이 나타나도, 그 문자열이 머신 소스에도 있으면 **우리가 출력한 것**이다.
매 회차 자동으로 검사해 해당 마일스톤을 무효화한다.

### 우회 기록

모든 우회는 `06_machine/bypasses.md` 에 네 항목으로 기록한다.

| 항목 | 내용 |
|---|---|
| 대상 | 무엇을 바꿨는가 |
| 이유 | 이 환경에서 왜 원본대로 동작하지 않는가 |
| 방법 | 어떻게 바꿨는가 (주소·인코딩 포함) |
| 부작용 | 이제 무엇이 검증되지 않는가 |

**부작용 항목은 이후 실행이 정체될 때 가장 먼저 참조된다.** 형식적으로 채우면 정작 필요한
시점에 쓸모가 없다.

## 6. 검증 (6항목)

```
1단계  verify.py       → verdict_script.json    (측정)
2단계  verifier 에이전트 → 원시 로그·바이트 재검증  (최종 판정)
```

| 방향 | 규칙 |
|---|---|
| 낮추기 (VERIFIED → UNVERIFIED) | verifier 판단이 우선. 의심스러우면 낮춘다 |
| 올리기 (UNVERIFIED → VERIFIED) | 바이트 수준 증거를 제시할 때만 |

| # | 항목 | 통과 조건 |
|---|---|---|
| 1 | 체인 실행 트레이스 | 스테이지 진입 PC 가 순서대로 등장 + 커널 진입 |
| 2 | 출력 바이트 대조 | 콘솔 토큰이 펌웨어 바이너리에 파일 오프셋으로 존재 |
| 3 | 소스 반증 | 머신 소스에 동일 출력 문자열 0개 |
| 4 | 검증 양방향 | 정상 이미지 통과 **그리고** 1바이트 훼손 시 실패 |
| 5 | 스토리지 이중 구동 | 부트로더 드라이버와 커널 드라이버가 **둘 다** 구동 |
| 6 | 우회 기록 | 네 항목으로 전부 기재 |

**게이트 3항을 모두 통과해야 `VERIFIED`.** 통과해도 부팅 완주를 뜻하지 않으며, 도달은 마일스톤으로 따로 본다.

### 항목 4 와 5 가 있는 이유

- **항상 통과하는 검증기는 항상 통과하는 스텁과 구별되지 않는다.** 훼손된 이미지가 실패해야
  검증이 실제로 수행됐다는 증거가 된다.
- **한 드라이버에 맞춘 스토리지 모델은 컨트롤러의 모델이 아니라 그 드라이버 기대치의
  모델이다.** 두 드라이버가 같은 모델을 구동해야 한다.

## 7. 기록

무엇을 왜 시도했고 어떻게 풀렸는지가 남아야 재개·재현이 가능하다.

| 파일 | 내용 |
|---|---|
| `JOURNAL.md` | 세션·회차·판단 경위 (사람이 읽음) |
| `rounds.jsonl` | 회차별 지문·분류·담당·변경·효과·**변경 사유** |
| `prompts.jsonl` | 사용자 입력 원문 |
| `resolutions.jsonl` | 정지점 해결 경위 |
| `blockers.jsonl` | 관측으로 확인된 하드 블로커 |
| `metrics.jsonl` | 시간·토큰 |
| `ANALYSIS.md` | 소요·비용·정체 구간·해결 경위 분석 |
| `RESUME.md` | 정지 시 인계 문서 |

- **사용자 입력은 요약하지 않고 원문 그대로** 남긴다. 실행이 멈췄을 때 어떤 지시로 그 방향을
  택했는지가 가장 먼저 사라지는 정보다.
- **fixer 를 지정한 회차는 변경 사유가 필수다.** 없으면 그렇게 표시되며, 사유가 없는 회차는
  나중에 무엇을 왜 바꿨는지 되짚을 수 없다.
- 틀린 가설도 지우지 않는다. 무엇을 배제했는지가 기록이다.
